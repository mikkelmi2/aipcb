# 0013 — Continuous integration, and the KiCad dependency

* **Status:** Accepted
* **Date:** 2026-08-23
* **Context:** milestone M15d, making the repository public. The test suite needs
  KiCad's symbol and footprint libraries, `kicad-cli`, `pcbnew` and a container
  runtime to exercise everything it covers, and a public GitHub runner has none of
  them. Builds on [ADR 0009](0009-pours.md), whose `pcbnew` boundary is what makes
  the resolution below possible at all.

## Context

The suite already degrades honestly: `tests/conftest.py` carries `skipif` markers
for KiCad's libraries, for `kicad-cli` and for `pcbnew`, and
`tests/test_simulation.py` for a container runtime with the pinned gerber2ems
image. A contributor without KiCad gets a green run, and everything that needed
KiCad says so by name rather than failing.

That is good for a contributor and not good enough for CI. A gate that silently
skips the parts that touch the real KiCad is a gate that would not have caught any
of the last three milestones' most expensive defects — M14's `check_design`
running DRC on an empty board, M13's silent routing bug, M10's fill boundary. The
question this ADR answers is what a public runner can actually be made to do.

## What was measured

All figures on 2026-08-23, with `podman` on the development machine (16 cores,
30 GB RAM, Linux 7.0.0-29-generic), against images pulled that day.

**Finding 1 — a pinned KiCad image exists, and it has everything.**
`docker.io/kicad/kicad:9.0.8` is published and is 1.7 GB. Pulling it cold took
**44.7 s**. Inside it:

| | |
|---|---|
| base | Debian GNU/Linux 12 (bookworm), x86_64, glibc 2.36 |
| `kicad-cli --version` | `9.0.8` |
| `pcbnew.GetBuildVersion()` | `9.0.8` |
| symbol libraries | 224 `.kicad_sym` files under `/usr/share/kicad/symbols` |
| Python | 3.11.2 |
| `git` | present — `actions/checkout` works normally |

That is the exact patch version every measurement in this repository was taken
against, which matters more here than anywhere: [`CLAUDE.md`](../../CLAUDE.md) is a
standing instruction to re-measure external tools rather than assume them, and a
floating `9.0` tag would quietly move the thing all the ADRs are calibrated on.
While confirming the tag existed we found `kicad/kicad:10.0.5` is also published —
so KiCad 10 is out, and **no measurement in this repository has been taken against
it**. That is a known debt, recorded here rather than discovered later.

**Finding 2 — the image needs two things done to it before it can run Python
tests.** Both were measured, neither is expensive:

* It runs as a **non-root user** by default, so `apt-get` fails with
  `Permission denied` on `/var/lib/apt/lists/partial`. GitHub Actions container
  jobs take `options: --user root`.
* It ships Python 3.11 with **neither `pip` nor `ensurepip`** — `python3 -m venv`
  creates an environment with no `pip` in it. `apt-get install python3-pip
  python3-venv` fixes it in **~11 s**, and installing aipcb into a venv takes
  another **~11 s**.

**Finding 3 — the PPA alternative was checked and rejected.** The
`~kicad/kicad-9.0-releases` PPA is live, but it tracks the newest 9.0 point
release rather than a pinned one, and it would have to be trusted to keep
supporting whatever Ubuntu `ubuntu-latest` becomes. The image pins the exact
build of both `kicad-cli` and `pcbnew`; the PPA pins neither.

**Finding 4 — and this is the one that changed the design. The full suite fails
in the image, and it is nothing to do with KiCad.**

Running the whole suite inside `kicad/kicad:9.0.8` on its Python 3.11 took
**32 m 21 s** and produced exactly one failure:

```
FAILED tests/test_multilayer.py::TestMultilayerRouting::
       test_a_protected_net_owns_the_corridor_and_the_other_detours[X1]
assert not [Unrouted(net='X2', ..., reason="the free area is split in two ...")]
```

The same test passes on the development machine. It is not flaky — it failed 3 of
3 in the image and passed 3 of 3 on the host. Bisecting it, with KiCad's libraries
mounted into stock `python:X-slim` images so that KiCad itself was held constant:

| Python | numpy | shapely | GEOS | result |
|---|---|---|---|---|
| 3.11.16 | 2.4.6 | 2.1.2 | 3.13.1 | **fails** |
| 3.12.14 | 2.5.2 | 2.1.2 | 3.13.1 | passes |
| 3.13.15 | 2.5.2 | 2.1.2 | 3.13.1 | passes |
| 3.14.7 | 2.5.2 | 2.1.2 | 3.13.1 | passes |

numpy is not the variable: pinning **numpy 2.4.6 under Python 3.14** — the older
library, the newer interpreter — passes. shapely and GEOS are identical across
every row. The interpreter is the variable.

The mechanism is CPython 3.12's change to `sum()`, which for floats now uses
Neumaier compensated summation:

```
py3.11: sum([0.1]*10 + [1e16, -1e16]) = 0.0
py3.12: sum([0.1]*10 + [1e16, -1e16]) = 1.0
```

`aipcb.route` sums float distances to cost a path — `geometry.py:299`,
`graph.py:140`, `meander.py:52` are all `sum(math.dist(a, b) for ...)` — and the
negotiated-congestion search compares those costs. A cost that differs in its last
bits flips a comparison, the search takes a different branch, and on this
deliberately-tight probe board one net ends up unroutable.

**This is a real defect and it is not CI's to fix.** The project's own rule is
that determinism is inviolable: same source in, byte-identical output out, on any
machine. That holds *within* a Python version and did not hold *across* the
3.11/3.12 boundary, while `pyproject.toml` declared `requires-python = ">=3.11"`.
The underlying defect is filed as an issue rather than patched here: the fix —
summing costs with `math.fsum` throughout — changes routing output on every
board and would move every golden file, which is a milestone of its own and not
a line in a CI ADR.

**The supported range was narrowed instead**, in this milestone: `requires-python`
is now `>=3.12`. Between shipping a version the router is wrong on and dropping
it, dropping it is the honest move — a 3.11 user today is not getting 3.11
support, they are getting different boards. The reason is written into
`pyproject.toml` beside the constraint, so nobody widens it back without reading
it.

## Decision 1 — two test jobs, and the KiCad one is the gate

CI runs the suite twice.

`test` runs on a bare `ubuntu-latest` with no KiCad, across the Python versions
the project claims to support (3.12 and 3.13). Measured there: **427 of 1274
tests run, 847 skip, in about 17 s.** Its job is to keep the no-KiCad path
working, which is the path every new contributor is on. It is allowed to skip;
what it must not do is fail.

`test-kicad` runs the same suite inside `kicad/kicad:9.0.8`, where those other
847 actually execute. This is the job that gates a merge, because it is the only
one that exercises the real ERC, the real DRC, the real zone filler and the real
`pcbnew` boundary. Two thirds of this suite is invisible to a runner without
KiCad, which is the whole argument for paying for the container.

## Decision 2 — inside the KiCad image, aipcb runs on a Python it works on, and
`pcbnew` keeps the system one

The obvious reading of Finding 4 is that CI is stuck: the KiCad image's `pcbnew`
bindings are built for its system Python 3.11, and aipcb is broken on 3.11.

It is not stuck, and the reason is [ADR 0009](0009-pours.md). aipcb never imports
`pcbnew` in its own process. `aipcb.kicad.fill` and `aipcb.kicad.specctra` are run
as *subprocesses* under an interpreter that is probed for `pcbnew`, in the
documented order `AIPCB_PCBNEW_PYTHON`, then `python3`, then `/usr/bin/python3` —
and those helpers import nothing from aipcb and nothing outside the standard
library, precisely so a system interpreter can run them.

So the two interpreters can differ, and here they should:

* **aipcb runs on Python 3.12**, installed into the image by `uv` as a standalone
  build, because that is a version the router is correct on.
* **`pcbnew` runs on the image's system Python 3.11**, because that is what
  KiCad's bindings were built for.

This is not a workaround bolted on for CI. It is the boundary ADR 0009 drew, being
used for exactly the thing it was drawn for: the version of Python aipcb wants and
the version KiCad's bindings need are allowed to be different.

## Decision 3 — the licence checks are CI's job too

Two checks that have nothing to do with tests run on every pull request, because
both catch drift that nobody would otherwise notice until it mattered:

* `tools/add_spdx.py --check` — every Python file carries its SPDX header.
* `tools/check_licenses.py` — every distribution in the *runtime* dependency
  closure is permissively licensed. Dev tools are excluded: they are not
  redistributed, so their licences do not propagate. Measured at the time of
  writing: 16 distributions, all BSD/MIT-family.

## Decision 4 — the DCO check is ours, not a third-party action

`tools/check_dco.py` is a few dozen lines of standard library. The alternative was
a marketplace action, which would mean an unreviewed third party running in CI on
every pull request from every contributor. For a check this simple that trade is
not worth making.

## Consequences

* A merge is gated on KiCad 9.0.8 behaviour, not on a mock of it.
* Two Python interpreters are in play inside one CI job. Anyone debugging that job
  must know which is which; the workflow prints both versions before running
  anything, on purpose.
* Pulling a 1.7 GB image on every run is the cost. It is paid in ~45 s of a job
  that then runs for half an hour, so it is not the thing to optimise.
* **`requires-python` is `>=3.12`.** Narrowed in this milestone rather than left
  as a claim the project could not support. It can widen again only when the
  summation defect is fixed and 3.11 is measured green, not before.
* KiCad 10 exists and nothing here has been measured against it. Re-measure at the
  next major, as [ADR 0009](0009-pours.md) already requires, and expect this ADR's
  image pin to move with it.
