# M12 — signal-integrity simulation: delivery report

`aipcb simulate` exists. It cuts one slice per differential pair out of a routed
board, hands each slice to openEMS through Antmicro's gerber2ems in the container
[ADR 0011](../decisions/0011-si-simulation.md) pinned, and turns the S-parameters
that come back into the same source-referenced findings as every other check.

Everything below was measured on 2026-08-21 on the development machine (16 cores,
30 GB RAM), on the tree as committed. Where a number is an estimate or a closed form
rather than a measurement, it says so.

## Deviations, stated loudly

| Item | What happened |
|---|---|
| *"one pair simulated on `examples/mcu-4layer`, results within a plausible sanity band of its design target"* | **Simulated and converged, but the band had to be defined against physics the design target does not model.** The USB pair reads **≈74 Ω** differential. Both closed forms aipcb carries say 121 Ω (IPC-2141) and 127 Ω (Hammerstad) — and both are *bare microstrip formulas applied to a trace with a ground pour 0.2 mm away on each side*. The pair is a coplanar waveguide with ground, not a microstrip, and a 40 % drop is what that does. The band chosen, and the argument for it, are below under "The calibration". |
| *"`examples/diff-pair`'s declared 100 Ω is unreachable"* | **Confirmed, with different numbers than phase 0 assumed.** ADR 0011 wrote ≈270 Ω from a loosely-coupled reading of Hammerstad. aipcb's own formulas, using its own coupling factor, give **151 Ω (IPC-2141) / 156 Ω (Hammerstad)** for that geometry. Either way 100 Ω is not reachable and the example's target is wrong; the correction is recorded here rather than left as a discrepancy between two documents. |
| Simulated impedance sits systematically **below** every class target | **Not a defect in the router and not fixed.** Same cause as the first row: every bundled example pours ground up to its pairs at the class clearance, and neither closed form aipcb derives widths from knows about coplanar ground. The widths the tool derives are therefore systematically narrow for the boards it actually builds. Recorded in `docs/roadmap.md`; fixing it means a CPWG model and regenerating every controlled-impedance example. |
| "worst-case deviation **and its location along the trace** where derivable" | **The deviation is reported; the location is not.** Locating an impedance discontinuity along a trace needs a time-domain reflectometry transform of the reflection data, which is a second piece of numerics with its own convergence questions. What is reported instead is the median, the minimum and the maximum of the impedance across the swept band, which bounds the excursion without claiming to place it. Deliberately not built. |
| `--parallel N` | **Not built, and measured rather than assumed.** openEMS already uses every core — it sustained 300–1270 MCells/s on sixteen here — so a second process divides the same cores. ADR 0011 Decision 4. |
| scikit-rf | **Not adopted.** The post-processing is forty lines of `cmath`; adding a numeric stack to the install path of a YAML-and-pydantic tool for that is a bad trade. Every run writes a Touchstone `.s4p` so anyone who wants scikit-rf has the data. |
| `aipcb export` now writes **two** drill files where it wrote one | **A change to what a fab receives**, made deliberately: gerber2ems globs for `*-PTH.drl` and `sys.exit(1)`s when the glob is empty, and splitting by plating is what KiCad's own dialog does by default. ADR 0011, "the drill file had a name nothing globs for". |
| The `.kicad_pcb` stackup disagrees with the source stackup | **Found by this milestone and deliberately *not* fixed.** `compile/board.py` writes KiCad three equal 0.48 mm dielectrics for `examples/pcie-sata`, where the source declares 0.2104 / 1.065 / 0.2104 mm — and impedance is derived from the source. Fixing it changes every existing board, which M12's guardrails forbid. Simulation uses the source stackup and says so. ADR 0011 Decision 2. |
| `epsilon_r` per dielectric, and core-versus-prepreg typing | **Still unreachable**, for the same byte-stability reason. `loss_tangent` was made reachable because it costs nothing (no example sets it, so no board moves) and because it is the single number that decides insertion loss. |
| Energy decay | **The runs do not converge in time the way the vendor's examples do.** gerber2ems's own `stub_short` decays to −70 dB; these slices plateau between −20 and −27 dB, because a slice with two plane layers and an artificial boundary is a resonant cavity. The consequence is a few percent of truncation noise, visible as |Sdd21| a little above unity. It is characterised below rather than hidden, and it is why `max_steps` is a bounded default. |
| Crosstalk, eye diagrams, IBIS, thermal, PDN | Out of scope by the milestone's own text; recorded in `docs/roadmap.md`. |

Nothing else was descoped.

## How a pair becomes a simulation

```
routed .kicad_pcb
   │
   ├─ logical_pairs()      12 declared pairs on pcie-sata → 11 physical links
   │                       (the transmit lane's two pairs and two capacitors are one link)
   │
   ├─ build_slice()        the pair's copper + everything near it, clipped to a
   │                       tight outline; the capacitors bridged; a straight launch
   │                       grown at each end; four Simulation_Port footprints
   │
   ├─ export_board()       kicad-cli plots it like any other board — ADR 0001 holds,
   │                       aipcb still writes no Gerber itself
   │
   ├─ write_inputs()       stackup.json from the *source* stackup, simulation.json,
   │                       netinfo.json
   │
   ├─ nets_in_gerbers()    read the export back before spending a minute on it
   │
   ├─ slice_digest()       sha256(slice.kicad_pcb + simulation.json + stackup.json)
   │                       → skip if unchanged
   │
   ├─ podman run           gerber2ems -a, geometry + two excitations + postprocess
   │
   └─ analyse()            mixed-mode extraction → Zdiff, RL, IL, verdicts, Touchstone
```

Four things in the slice are not on the real board, and each is an approximation
with a reason:

* **The coupling capacitors become copper.** At 4 GHz a 100 nF capacitor is a
  milliohm; the part under test is the trace on both sides of it. aipcb knows which
  parts those are because the source says `role: ac_coupling` — this is the one place
  where a source-level slicer can do something a geometric one cannot, and on
  `examples/pcie-sata` it is the difference between one 18 mm link and two 10 mm
  stubs with a port in the middle of a capacitor.
* **Each end grows a 1.5 mm straight launch.** openEMS builds a microstrip port
  along a grid axis; a trace that ends on a diagonal at a pad has nowhere to be fed
  from. The port occupies exactly the launch, so it adds no trace — but the pad and
  its antipad are replaced by a uniform line, and the discontinuity that was really
  there is not modelled.
* **The corridor the launches occupy is cleared** of other nets' copper. Past the
  pad is the component, and with the footprints gone that region holds the next
  pins' fanout — on `examples/pcie-sata`, a ground track within a millimetre of every
  pair end. See failure 5 below.
* **Footprints are dropped.** The interior of a run, which is what an impedance
  target is about, is untouched. The last few tenths of a millimetre at each end are
  not modelled.

## Five silent failures, and what caught each one

Phase 0's most useful conclusion was that this integration's failure mode is a
confident wrong answer at a zero exit code, and that whatever aipcb built must assert
the solver saw its inputs rather than trusting the exit status. That turned out to be
exactly right — and to be an understatement. Two of the five below were in the export
(phase 0 predicted them), one was in KiCad's behaviour on a board with no footprints,
and **two were in the slicer this milestone wrote**. Every one of them produced a
board that looked correct, a solver that exited zero, and a number that was wrong.

### 1. The placement file was in the wrong frame (found by reading the file)

Phase 0's fix gave the file a name the consumer globs for. It did not give it the
right *coordinates*: `pcb export pos` defaults to absolute page coordinates, so every
row read like

```
"C1","C_100N_0603","C_0603_1608Metric",145.500000,-122.500000,0.000000,top
```

— the board's position on an A4 sheet, with KiCad's downward Y. Adding
`--use-drill-file-origin` turns that into `45.500000,21.500000`: the part's position
on the board. Verified by reading the exported rows back against the board's own
footprint positions, because the *drill* half of this bug survived a flag that was
already correct, and a test that checks flags would have missed both.

### 2. The drill file had a name nothing globs for

`<board>.drl`, one `MixedPlating` file. gerber2ems globs `*-PTH.drl` and exits 1.
Now `--excellon-separate-th`, which is KiCad's own default in the GUI. This changes
the fabrication package for every design and is flagged as a deviation above.

### 3. KiCad prunes padless nets by renumbering — the one nobody predicted

A slice has tracks and, before this fix, no footprints at all. `pcbnew` drops every
net that no pad references when it loads a board, and it drops them by
**renumbering**: the tracks keep their stored codes, which now point at other nets.
On the first `mcu-4layer` slice that actually ran end to end, the pair's copper came
back labelled `DEV_DM` / `DEV_DP` — its neighbours.

Measured, on that run:

| | |
|---|---|
| Segments in the slice board | 18 `USB_DM`, 17 `USB_DP`, 2 `DEV_DM`, 2 `DEV_DP` |
| Draws in the exported `F_Cu.gbr` under `%TO.N,DEV_DM*%` | **40** |
| Net names the Gerber carried | `DEV_DM`, `DEV_DP`, `GND`, `VBUS` — no `USB_*` |
| What gerber2ems then refined the mesh around | nothing |
| Resulting grid on a 12.5 × 17.5 mm slice | 109 × 109 × 62, **114 µm** average cell |
| What that does to a 0.25 mm trace with 0.2 mm of clearance | merges it into the ground pour it sits in |
| What came back after 4 min 16 s of solving | S₀₀ = −1.005 (a short), \|S₁₀\| = 0.0007 |
| Exit code | **0** |

The fix is two-part and both parts matter. Each port footprint carries one 50 µm pad
on the launch it sits on — copper entirely inside a 200–250 µm trace, so no geometry
moves, and the net survives the load. And **every run now reads its own Gerbers back**
before starting the container: if the pair's net attributes are not in the copper
Gerbers, the pair fails with a diagnostic instead of being solved for a minute and
answered wrongly.

After the fix, the same slice: `USB_DM` and `USB_DP` present in the Gerber, grid
105 × 152 × 28 at the *coarsest* setting tried, \|S₁₀\| = 0.95.

### 4. The two launches of one pair ran on the same line — ours

The launch direction was the average of the two traces' outgoing directions. That is
right for a pair that runs *along* the board and wrong for a pair that leaves its pads
**broadside** — and `examples/pcie-sata`'s three PCIe lanes leave the controller
exactly like that: 0.5 mm apart in x, both heading down the board. The average comes
out along x, both launches run on one line, they overlap, and P is welded to N.

Measured on the transmit lane before the fix, with a completely plausible-looking
board:

| | before | after |
|---|---|---|
| peak \|Sdd21\| | **7.26** | 1.14 |
| worst return loss | **+40.7 dB** | −8.3 dB |
| differential impedance | **436.6 Ω** against 85 Ω | 66.6 Ω |
| energy decay | −35 dB, plateaued | **−70 dB** |
| exit code | 0 | 0 |

The rule is now perpendicular to the pair's own separation, with only the *sign* taken
from where the conductor heads. Five of pcie-sata's twenty-two pair ends were
collinear before it; a test now asserts the property on every pair on the board.

The verdict machinery did its job here — the run came back `impedance=unusable` on the
\|Sdd21\| > 1.15 rule, so nothing wrong was ever reported as a result. But it was one
threshold away from being reported as an impedance, and finding it took reading the
copper rather than reading the numbers.

### 5. The launch ran out past the pad, into the next pin's fanout — also ours

Subtler, with no wrong-looking geometry at all. A launch runs *outward* from where the
pair ends. Where a pair ends is a pad, and past the pad is the component. A slice drops
the footprints, so that region is not empty — it is the neighbouring pins' escape
routing. Measured on `examples/pcie-sata`: **every one of the twenty-two pair ends has
a ground track crossing within a millimetre of it.** A 1.5 mm launch laid straight
through is shorted to ground, and the first working batch was doing that on all eleven
pairs.

Shortening the launch until it fits was tried first and measured badly: on this board
there is frequently no collision-free length at all, so every port collapsed to a
0.4 mm floor — two trace widths, too short to de-embed. What ships instead **clears the
corridor**: foreign tracks are cut where they cross it, vias inside it are dropped, and
the slice reports how much it removed.

| Pair | foreign track removed | vias dropped |
|---|---|---|
| `PCIE_TXN+PCIE_TXP` | 5.02 mm | 0 |
| `SATA2_RXN+SATA2_RXP` | 4.02 mm | 0 |
| `SATA2_TXN+SATA2_TXP` | 3.90 mm | 1 |
| `REFCLKN+REFCLKP` | 3.61 mm | 1 |
| `PCIE_RXN+PCIE_RXP` | 2.48 mm | 0 |
| the other six | 1.00–2.32 mm | 0–1 |

That is a deliberate modification of the same kind as dropping the footprints and
bridging the coupling capacitors: **the port stands in for the pad and for everything
past it** — the driver, the connector, the cable — and the neighbouring pins' fanout is
not the transmission line under test. What matters is that it is visible: it is in the
slice's own `notes`, in `--json`, and in the console output.

## The source block, and what it does not contain

```yaml
simulation:
  classes:
    sata:    { stop_ghz: 6.0 }     # SATA III: 3 GHz fundamental
    pcie_tx: { stop_ghz: 8.0 }     # PCIe Gen3: 4 GHz fundamental
    pcie_rx: { stop_ghz: 8.0 }
```

That is the whole of what `examples/pcie-sata` had to say. Everything else —
which nets are a pair, which capacitors are shorts, what the laminate is, what the
impedance target is, which plane each pair is referenced to, how wide the trace is —
was already in the design, because M8 through M11 put it there. Mesh density, slice
margin and the pass thresholds are settable and are left at their defaults.

`impedance_tolerance`, `return_loss_db` and `insertion_loss_db` default to ±10 %,
−10 dB and −3 dB. **These are engineering defaults, not standards compliance.** Ten
percent and −10 dB are what most controlled-impedance fabrication notes ask for;
nothing here certifies a design against PCIe or SATA, and a link with a real budget
should state its own numbers.

Adding the block to `examples/pcie-sata` left its `.kicad_pcb`, `.kicad_sch` and
`.kicad_pro` byte-identical to the golden files — verified before anything else.

## What a run leaves behind

`out/si/<pair>/` per pair:

| File | What it is |
|---|---|
| `slice.kicad_pcb` | the slice, openable in KiCad and byte-stable |
| `slice.json` | the ports, the outline, the conductor length, and any notes |
| `fab/` | the slice's Gerbers, drill and placement file, plus `stackup.json` |
| `simulation.json`, `netinfo.json` | what gerber2ems was told |
| `ems/` | the solver's own geometry, S-parameters and plots |
| `<pair>.s4p` | the raw S-matrix as Touchstone, for scikit-rf or anything else |
| `result.json` | the cache entry: the digest, the timing and the metrics |
| `run.log` | the full solver log, which a failure's hint points at |

and `manifest.json` beside them, recording every pair, its status, its digest, its
wall clock and the image digest the batch actually ran on.

The Touchstone file says what it does not know: only two of the four columns were
excited, because a differential pair needs both halves of one end driven and the
other two columns are the reciprocal of those. The header states it rather than
letting a reader assume a full four-port sweep.

## What this does not tell you

Stated here as plainly as M11e stated its own limit, because the number that comes
out of a field solver is more persuasive than the number that comes out of a rule and
therefore needs the caveat more, not less.

**The stackup simulated is the one the source declares.** Every impedance below is
computed from `layout.stackup` — the prepreg thickness, the permittivity, the
dissipation factor written in the design file. A fabricator who presses a different
prepreg builds a different impedance and nothing here will know. This validates the
*layout*: it finds a pair routed at the wrong width, a reference that is not where
the class said, a discontinuity a via transition introduced. It does not replace an
impedance coupon on the panel or a measurement on the finished board.

**The thresholds are engineering defaults.** ±10 % and −10 dB are conventional, not
normative. Nothing here is a compliance statement.

**The launch is not the pad.** Each port replaces the last 1.5 mm of the pair with a
uniform line of the same width. A real pad, its antipad in the plane and the fanout
neck into it are discontinuities that this deliberately does not model — so the
numbers describe the *run*, and a design whose problem is at the pad will look
cleaner here than it is.

**The energy does not fully decay.** gerber2ems's own validated example settles at
−70 dB; these slices plateau between −20 and −27 dB because a slice with plane layers
and an artificial boundary is a small resonant cavity. The residual shows up as a few
percent of noise, and as |Sdd21| a little above unity — above unity is physically
impossible and is a marker phase 0 used to call an extraction broken, so the
threshold that separates "truncation noise" from "broken" is *calibrated against
measured data*: phase 0's genuinely non-converging diff-pair slice peaks at 1.166,
these runs at 1.07–1.09, and the line sits at 1.15.

## The reuse-versus-reimplement call

Phase 0 left this open, and the answer is **reimplement**. Antmicro's
`kicad-si-simulation-wrapper` targets KiCad 9 and generated the very examples phase 0
validated against, so it was a serious candidate. Four things decided against it, in
descending order of weight:

1. **A geometric slicer cannot know what a part is.** `examples/pcie-sata`'s transmit
   lane is four nets, two declared pairs and two capacitors, and it is *one*
   transmission line. The wrapper cuts a region out of a board; it has no way to know
   that `C2` and `C3` are shorts rather than components under test. aipcb does,
   because the source says `role: ac_coupling` — this is the milestone's own stated
   reason to prefer its own slicer, and on the flagship example it is the difference
   between one 18 mm link and two 10 mm stubs with a port inside a capacitor.
2. **It works through the `pcbnew` Python API, which aipcb deliberately keeps at
   arm's length.** ADR 0009 confines that import to a subprocess behind a version
   lock, for zone filling only. Adopting the wrapper would put it in the tool's own
   process.
3. **A slice has to be an aipcb board.** Same s-expression writer, same deterministic
   UUIDs, same stackup arithmetic — which is what makes "slice generation is
   byte-stable" a property rather than a hope.
4. **What was worth taking was the method, and the method is three sentences.** Crop
   to a region; put `Simulation_Port` footprints at the trace ends; hand the result to
   gerber2ems. That is reproduced here, and phase 0 had already reproduced it by hand.

The honest cost: port placement, launch construction and the mixed-mode extraction
were all ours to get right, and two of the three were wrong on the first attempt.
Reuse would not have avoided that — the wrapper's ports are placed by a human in
KiCad — but it belongs on the ledger.

## Determinism

| Property | Result |
|---|---|
| Slice generation | **Byte-stable.** Slicing the same routed board twice produces identical files; a test asserts it. UUIDs are hashes of the pair name and the element index, never of order. |
| Solver numerics | **Not bit-reproducible**, and openEMS makes no such claim: it is a threaded FDTD kernel whose reduction order depends on scheduling. |
| Verdicts | **Reproducible.** What the gate needs is that pass/warn does not flip between runs, and the mesh convergence study below bounds the run-to-run spread far below any threshold in use. |
| Every golden board | **Byte-identical** after every change in this milestone, including the `simulation:` block added to `examples/pcie-sata` — checked against all eleven examples' `.kicad_pcb`, `.kicad_sch` and `.kicad_pro`. |

## The calibration

Phase 0 set a condition on this milestone: *do not report an impedance number until a
known-good structure reproduces a known-good value.* It also said why the numbers on
`examples/diff-pair` moved by 3× between runs — a 0.25 mm trace 1.51 mm above its
nearest copper barely guides at all — and named `examples/mcu-4layer` as the board to
calibrate on instead: its In1.Cu GND plane sits 0.48 mm below F.Cu.

The pair is `USB_DM/USB_DP`, 0.25 mm wide at a 0.2 mm gap, on F.Cu over that plane,
with the board's GND pour 0.2 mm away on each side. Three mesh densities of the same
geometry:

| Mesh | grid | cells | wall clock | \|Sdd21\| peak | Zdiff | ripple min–max | group delay |
|---|---|---|---|---|---|---|---|
| coarse — 100 µm, 6 cells per dielectric | 105 × 152 × 28 | 0.45 M | **54 s** | 1.075 | **75.96 Ω** | 16–201 Ω | 134.7 ps |
| shipped default — 50 µm, 8 | 181 × 290 × 39 | 2.05 M | **390 s** | 1.056 | **74.19 Ω** | 25–156 Ω | 125.9 ps |
| fine — 25 µm, 16 | 247 × 331 × 62 | 5.07 M | **1371 s** | 1.065 | **78.12 Ω** | 31–156 Ω | 128.4 ps |

**The answer moves by 5.3 % across an 11-fold change in cell count and a 25-fold
change in run time.** That is the condition phase 0 attached to this milestone,
discharged: on `examples/diff-pair` the same exercise moved the answer by 3×. The
difference is the structure, exactly as phase 0 predicted — a plane 0.48 mm below the
trace guides, one 1.51 mm below it does not.

Two supporting checks that the ports are measuring the trace and not something else:

* **Group delay.** 20.7 mm of conductor came back at 126–135 ps, against the 126 ps
  that 6.1 ps/mm predicts for FR-4 microstrip. Two undeembedded 1.5 mm launches would
  have added 18 ps, so openEMS is de-embedding them as intended.
* **Energy.** No run reports gain worth calling broken: peak \|Sdd21\| is 1.06–1.08
  where phase 0's non-converging slice reached 1.166.

50 µm and 8 cells per dielectric is what ships: it is within 5 % of the finest run
at a fifth of its cost, and the difference is well inside the ±10 % that a verdict
turns on.

### The sanity band, and why the design target is not it

The acceptance clause asks for a result "within a plausible sanity band of its design
target". The `usb` net class on `examples/mcu-4layer` declares no
`impedance_diff_ohm` at all — its target is implicit in its geometry — so the band has
to be built from what that geometry should give. aipcb's own two closed forms say:

| Model | Z₀ single-ended | Coupling factor | **Zdiff** |
|---|---|---|---|
| IPC-2141 (what the width solver uses) | 89.6 Ω | 0.678 | **121.5 Ω** |
| Hammerstad (what M8's gap estimator uses) | 93.3 Ω | 0.678 | **126.5 Ω** |
| **Simulated** | | | **74–78 Ω** |

That is 40 % low, and it is not noise: three mesh densities agree on it. The reason is
that **both formulas are bare-microstrip models and this is not a bare microstrip.**
`examples/mcu-4layer` pours GND on F.Cu, and the pour comes to within the class's
0.2 mm clearance of each trace. A pair with ground 0.48 mm below it *and* 0.2 mm
either side of it is a coplanar waveguide with ground, whose impedance is
substantially lower than the microstrip the formula solved for.

So the band chosen is: **the simulated impedance must lie between the coplanar limit
and the microstrip limit, and nearer the coplanar one.** It does, and the sign is
right — coplanar ground can only pull the impedance *down*, never up. A simulated
result *above* 121 Ω would have meant the model was wrong; a result at 74 Ω means the
formula is answering a question about a different board.

That is a finding about `impedance.py`, not about the router, and it is the most
useful thing this milestone measured. It also predicts what the flagship board will
do: `examples/pcie-sata` pours ground the same way, so every pair on it should come
back below its declared target by a similar fraction. It does — see the next section.

## Open questions

* **The impedance formulas do not know about coplanar ground, and every board here
  has it.** This is the biggest single finding and it is not a simulation problem: it
  is that `impedance.py` derives a width from a bare-microstrip model, and then the
  pour comes within a class clearance of the trace and moves the answer. The
  simulated numbers are consistently below target by a similar fraction on every
  pair, which is the signature of a model error rather than a routing error. Fixing
  it means a coplanar-waveguide-with-ground model and regenerating every
  controlled-impedance example, so it is recorded rather than done.
* **Should the pour keep further away from a controlled-impedance pair?** The other
  side of the same coin, and a design question rather than a code one. A pour at
  3 × the class clearance would make the microstrip model true again; a pour at 1 ×
  gives better shielding and a lower impedance than anyone asked for. Nothing in
  aipcb has an opinion today.
* **The slice's boundary is a resonator.** Energy plateaus around −20 to −27 dB
  instead of decaying to −50, which costs a few percent of accuracy. A perfectly
  matched layer boundary, or lossier plane material, would help; gerber2ems calls
  `set_boundary_conditions(pml=False)` and does not expose the choice.
* **A digest-pinned Containerfile.** Phase 0 already recorded that upstream pins its
  base image by tag and installs from moving apt archives, so `aipcb simulate` is
  pinned by *image* and not reproducibly rebuildable. Unchanged.
* **`aipcb export` still ships an unrouted board.** Phase 0's gap 10. `aipcb
  simulate` works around it by routing for itself; the surprising default is still
  there.
* **Crosstalk is present but not measured.** A slice carries its neighbours' copper,
  so their loading is in the answer — but nothing excites them and nothing reports
  pair-to-pair coupling. That is the obvious next stage and is in
  `docs/roadmap.md`.

## The two pairs M11 left open

M11's own report flagged one thing as its closest call: `REFCLKP/N` and `PCIE_RXP/N`
are *delivered* at **0.292 mm** and **0.256 mm** of intra-pair skew against the
**0.125 mm** their class declares — routed and annotated rather than handed over. The
milestone owner's question for M12 was whether simulation discriminates.

It does, but not where one might look first. **Impedance cannot see skew**: a pair
with a length mismatch has the same cross-section as one without, and both read the
same differential impedance. What skew does is convert differential signal into
common mode, and that is a quantity the same four-port matrix already contains —
Scd21, differential in, common out. M12c reports it for that reason.
