# M11 — controlled impedance, card edges, via transitions & high-speed verification: delivery report

**Delivered, and this report is a reconstruction.** All of M11a–M11e, its tests,
`docs/format.md`, `docs/roadmap.md` and [ADR 0010](../decisions/0010-highspeed.md)
were built and committed across five commits (`4599b95`, `fbd048e`, `166fa4f`,
`e33b0ce`, `1e0a6a2`) by one session, which was then terminated by an
infrastructure failure — an API session limit — at the moment it said *"Now the
performance measurements:"*. This report was written afterwards, in a separate
pass over a clean tree at `1e0a6a2`, by someone who did not write the code.

Everything below is either **measured here, on a quiet machine, in this pass**, or
attributed to the ADR and the commit messages that the implementing session wrote.
Where the two disagree, the measurement wins and the disagreement is stated. Where
something could not be determined from the repository, it says so rather than
inventing an account. It is not a live record of how the work went, and it should
not be read as one.

## Deviations, stated loudly

Everything not delivered as the specification wrote it, in one place and at the top.

| Item | What happened |
|---|---|
| *"the M11e report runs clean (no reference-plane crossings, stubs under threshold) on everything that routed"* | **Two of twelve pair objects do not run clean.** Reference continuity and via stubs *are* clean — 629.3 mm projected, **0** plane crossings, worst stub **0.000 mm** against a 0.5 mm threshold, width and gap deviation **0.0** on all twelve. Skew is not: `REFCLKN+REFCLKP` comes out **0.292 mm** and `PCIE_RXN+PCIE_RXP` **0.256 mm** against the **0.125 mm** their class declares, and both are *delivered* rather than handed over. Discussed at length under "The skew question" — it is the one place in this milestone where the delivered result sits closest to the marginal delivery the milestone exists to prevent. |
| The `diff-pair` copper sliver | **Not resolved, and it was expected to be.** The kickoff expected M11d rule 1 to close it. Measured here: the routed, unfilled board still carries exactly **one** `copper_sliver` warning. Rule 1 could not have closed it — it applies only to classes naming an `impedance_diff_ohm`, and `diff-pair`'s `lvds` class names none (measured: `standoff` 1.0, `target_ohm` null). Full verdict below. |
| `standoff_k`'s own default | **Unusable on the milestone's own reference board.** The default is 3; `examples/pcie-sata` sets **1.4**, with the arithmetic written into the source. At k = 3 every pair on that board is refused. The rule works — it refuses correctly and names itself in the hint — but a default that no bundled board can take is a default worth flagging. |
| Net-class field names | **Renamed.** The specification writes `impedance_diff`, `max_skew`, `max_uncoupled` and `class: diff_pair`. The implementation spells the unit into each — `impedance_diff_ohm`, `max_skew_mm` (reused from M7), `max_uncoupled_mm` — and does **not** implement `class: diff_pair` at all, because pair-ness already comes from `diff_pair:` on the nets. Recorded in ADR 0010 under "The naming deviation"; repeated here because a reader following the specification will type four field names that do not exist. |
| A KiCad warning that cannot be removed | **`lib_footprint_mismatch` on every card-edge board.** ADR 0010 Decision 2 gives the board outline one author, which means placing the edge footprint without its own `Edge.Cuts`, which means it is no longer byte-identical to its library copy. Measured: `aipcb check examples/pcie-sata` returns **1 DRC warning and 0 DRC errors**, and that warning is this one. There is no version of this that has both. |
| Two contacts on the reference board are not connected at all | **PERST# and the A1–B17 presence-detect strap are absent from the netlist**, not handed over. Both must cross all three lane pairs and a sig/gnd/pwr/sig stackup has no signal layer left to cross on. The source says so in a comment; `docs/roadmap.md` records it. The consequence for the numbers: `90/90 routed` counts 90 connections that exist, and does not count two a real card would need. |
| No pair was handed over | The milestone's own framing was *"a human finishing 2 of 11 pairs manually is success"*. **Eleven of eleven routed as coupled pairs, and nothing reached M9f.** That is a better result than the bar, but it means the reference board does not exercise the hand-over path at all; the two M11d rules that *can* force a hand-over — the standoff corridor and the coupling budget — are proved by purpose-built fixtures in `tests/test_highspeed.py`, not by the shipped example. |
| AC-coupling capacitor *placement* | **Validated and measured, never moved.** `role: ac_coupling` checks that the two capacitors sit level across the pair's travel and reports how far out they are; the placer does not position them. Recorded in ADR 0010 and `docs/roadmap.md`. |
| Impedance derivation covers outer layers only | **Surface microstrip, and nothing checks that you asked for it.** A class routed on an inner layer between two planes is stripline, a different formula, and today it gets a microstrip width back with no warning. No bundled design does this; nothing stops one. Recorded in `docs/roadmap.md`. |
| "M11d is the only permitted stretcher change" | **`src/aipcb/route/stretch.py` was not touched.** The three rules landed in `route/pairs.py` (+425/−10), the coupled-pair path. Not a deviation from the letter — it is narrower than the guardrail allowed — but a reader looking for M11d in the stretcher will find nothing there. |
| Suite runtime | **Up from 13 m 57 s to 20 m 27 s** (1090 tests, up from 968). Measured here, not estimated. The new board is the expensive part — routing `pcie-sata` costs 36 s each time a test class does not have it cached — but the split between it and the 73 new unit tests was not separately measured. |

Nothing else was descoped.

### The skew question, and whether the treatment is defensible

The specification's own wording is *"any pair that cannot meet the rules is handed
over via M9f with reasons, never delivered marginal"*. Two pairs are delivered
outside a number their class declares, so it is worth being explicit about which
side of that line they fall on.

**What is measured.** Half-conductor lengths, read off the router's own record:

| Pair | Positive half | Negative half | Out of length | Budget | As a fraction of the run |
|---|---|---|---|---|---|
| `REFCLKP/N` | 21.2157 mm | 20.9241 mm | **0.2916 mm** | 0.125 mm | 1.4 % |
| `PCIE_RXP/N` | 20.7427 mm | 20.9982 mm | **0.2555 mm** | 0.125 mm | 1.2 % |

They are exactly the two pairs a via transition splits, and they are the only two
pairs on the board over budget. The transition column itself is *not* the
asymmetry: the four signal vias sit symmetric about the point the source named to
within 7 µm (`REFCLKN` at +0.2749/−0.0072 mm from centre, `REFCLKP` at
−0.2749/+0.0072 mm). What the transition costs is the splay to the opened-out
0.55 mm via pitch at each end plus the two fan-outs it creates where there was one,
and `_match_lengths` reports there is no fan-out leg long enough to meander the
difference into.

**The case for the treatment being correct.** Skew is not one of M11d's three
rules. The three that force a hand-over are the standoff corridor, the wall-hugging
flag and the uncoupled budget; skew is an M11e *reporting* item, severity warning
by default, promotable to an error with `verify: error` on the class. Nothing was
silenced: six warnings across the two pairs, four `diff-pair-skew` and two
`hs-skew`, all carrying the number. The budget was **not** widened to fit — the
source's own comment records that the SATA class's first draft was 0.127 mm, that
one pair missed it by 49 µm, and that the class was rewritten with an argument
rather than tuned until the warning went away. And, on a first-principles estimate
made here: microstrip on this stackup at εr 4.4, h 0.2104 mm, w 0.2888 mm gives
εeff ≈ 3.25 and a delay of ≈ 6.0 ps/mm, so **0.292 mm is ≈ 1.8 ps against a Gen3
unit interval of 125 ps** — about 1.4 % of a UI. That is a number a link budget
absorbs without noticing.

**The case against.** The class declares 0.125 mm. It is not an inherited default;
somebody wrote it. A pair delivered at 2.3× its own declared budget is a pair the
source and the board disagree about, and the mechanism that exists to make that
disagreement fatal — `verify: error` — was available and not used. The acceptance
clause *"the M11e report runs clean … on everything that routed"* is, on the
measurement, **not met**.

**The verdict this report takes.** The treatment is defensible, and the acceptance
clause is still missed. Those are both true and it is worth keeping them apart. It
is defensible because the failure is loud, quantified, tied to a named cause, and
because the alternative on offer was not "a better pair" but "no PCIe lane at all
on a four-layer stackup" — the pre-M11c behaviour, where a pair that had to change
layer was simply refused. What would make it indefensible is the budget being
edited to 0.3 mm, and it was not. But *"runs clean"* is what the milestone asked
for, and 10 of 12 is not 12 of 12; it belongs in the deviations table, which is
where it is.

The honest framing for anyone reading the board rather than the report: **the eight
SATA pairs are finished work. The PCIe lane is routed, measured and annotated, and
a Gen3 sign-off still wants a human and an SI tool** — which is what
`summary.highspeed.method` says in the report itself: *"rule-based geometry checks,
not electromagnetic simulation"*.

## The `diff-pair` copper sliver: an expectation that was not met

The milestone kickoff told the implementing session that M11d's rules were
*expected* to resolve the known copper sliver on `examples/diff-pair`, and to flag
it prominently if they did not. **They did not.** Measured here rather than
inferred:

| Board | Command | `copper_sliver` |
|---|---|---|
| `diff-pair`, routed, **unfilled** | `aipcb route all` then `kicad-cli pcb drc --severity-all` | **1** (warning, F.Cu) |
| `diff-pair`, routed, **filled** | `aipcb check` | **0** |

The track geometry is unchanged by M11. Why rule 1 could not have touched it, from
the code and from the same measurement run: **M11d applies only to a class that
names an `impedance_diff_ohm`, and `diff-pair`'s `lvds` class names none** — its
pair audit comes back with `standoff: 1.0` and `target_ohm: null`, so the standoff
corridor never ran on that board at all. `docs/roadmap.md` adds that the sliver is
between two **GND** tracks rather than between the pair's halves, which would put
it out of rule 1's reach even on a controlled-impedance board.

That last point is the one thing here I **could not verify independently**: KiCad
9.0.8 reports this violation with an empty `items` array and no position, in both
the JSON and the report format, so DRC does not say which copper it is between.
The claim that it is between two GND tracks is the implementing session's, taken
from `docs/roadmap.md` and `tests/test_routing.py`, and this pass could not confirm
or refute it.

The marker in `tests/test_check_loop.py` — `"diff-pair": frozenset({"kicad-copper-sliver"})`
— is **left standing and must stay standing**. It is a permissive allowance rather
than a required outcome, so it is vacuous under `aipcb check` today (which reads
the filled board, where the pour closes the wedge); it is live in
`tests/test_routing.py::ALLOWED_VIOLATIONS`, which reads the unfilled one. Retiring
it would delete the record of a defect that is still in the copper a fabricator
receives before the pour is drawn. To the implementing session's credit it was not
touched.

## The four `pcie-sata` known issues

`tests/test_check_loop.py` gained a `pcie-sata` entry with four codes and the
reasoning written into the file. Measured here, each one:

| Code | Count | What it is, measured |
|---|---|---|
| `diff-pair-wall-hugging` | **3** | M11d rule 2, flag standing after one failed re-tighten. `PCIE_TXN+PCIE_TXP` beside `U1.17` and `U1.20`, both at **0.261 mm for 0.774 mm**; `REFCLKN+REFCLKP` beside `U1.14` at **0.218 mm for 0.899 mm**; `PCIE_RXN+PCIE_RXP` beside `U1.22` at **0.257 mm for 0.796 mm**. Threshold: closer than 3 × the 0.15 mm gap (0.45 mm) for longer than 5 × it (0.75 mm). All three were re-tightened with the offending pads' clearance inflated; the audit records `retightened: true, resolved_by_retighten: false` for each. **This is the outcome rule 2 specifies. Defensible without qualification.** |
| `diff-pair-skew` | **4** | Two pairs, reported twice each — see the reporting wart below. From `_match_lengths` at 0.251 mm (REFCLK) and 0.249 mm (PCIE_RX); from `measure_skew` over the whole conductor at 0.292 mm and 0.256 mm. |
| `hs-skew` | **2** | M11e restating the whole-conductor numbers — 0.292 mm and 0.256 mm — after meanders. **Closer to a marginal delivery than the wall-hugging flag is, and argued out above.** |
| `kicad-lib-footprint-mismatch` | **1** | The card-edge footprint placed without its own `Edge.Cuts`, so it no longer matches its library copy. The unavoidable price of ADR 0010 Decision 2. It is the board's **only** DRC finding, and it is a warning; DRC errors are 0. |

**A reporting wart found while measuring, not fixed.** The same pair is reported
out of budget **three times, with two different numbers** and no label saying why
they differ. `route/pairs.py::_match_lengths` warns per routed *segment* while it is
still trying to meander (0.251 mm for the reference clock); `measure_skew` then
warns again over the *whole conductor*, via barrels included (0.292 mm for the
same pair); and M11e reports the second number a third time as `hs-skew`. Six
warnings for two pairs. Nothing is wrong with any individual number — they measure
different things — but a reader gets "REFCLKN+REFCLKP is 0.251 mm out of length"
and "REFCLKN+REFCLKP is 0.292 mm out of length" three lines apart with no
explanation. Reported here rather than corrected, because this pass documents and
measures the delivered code rather than changing it.

## Per-pad-instance keying, re-verified against the shared-UUID defect

`docs/roadmap.md` records that pads sharing a *number* share a UUID, and M11's
brief warned this was where an edge connector would bite hardest. Re-measured here
on the boards this milestone actually builds:

| Component | Footprint | Pads | Distinct numbers | Distinct pad UUIDs |
|---|---|---|---|---|
| `J1` (the card edge) | `Connector_PCBEdge:BUS_PCIexpress_x1` | **36** | **36** | **36** |
| `J2`–`J5` (SATA) | `Connector_JST:JST_GH_SM07B-GHS-TB…` | 9 | 8 | **8** |
| `U1` | `Package_DFN_QFN:QFN-48-1EP_7x7mm_P0.5mm` | 65 | 50 | **50** |
| `usb-port`'s `J1`, for comparison | `Connector_USB:USB_Micro-B_Amphenol_10103594-0001LF_Horizontal` | 17 | 6 | **6** |

* **The defect does not bite the card edge at all.** KiCad's PCIe x1 footprint
  numbers every contact distinctly, `A1`–`A18` and `B1`–`B18`, so each finger has
  its own identity in the file as well as in the router. That confirms ADR 0010's
  Finding 4 independently.
* **The defect is still there, on the same board.** Each JST connector has two
  shell tabs both numbered `MP` sharing one UUID, and each QFN has sixteen
  exposed-pad sub-pads numbered `49` sharing one. The router tells them apart
  because `route.obstacles` keys on `reference#index` and never on the UUID.
* **`usb-port` is unchanged**: **31 pads carrying 20 distinct UUIDs**, with twelve
  pads numbered `6` sharing one. Exactly the figure M10 recorded, so nothing in M11
  moved it either way.

### What commit `1e0a6a2` actually found

The commit titled *"the keepout the UUID index had not heard of"* is not about pad
UUIDs. It is about the **one zone in this toolchain that nobody declares**: M11b
puts a pour keepout round a card edge's finger field, generated from the
connector's placement rather than written in `pours:`, and nothing mapped its UUID
back to source. Reproduced here by building the index with and without the fix and
running the same synthetic DRC violation through `checks/kicad_reports.py`:

| Index | Where the violation points | Hint |
|---|---|---|
| **as shipped** | `examples/pcie-sata/design.yaml:451:3`, path `('placement', 'J_PCIE')` | the real edge-clearance hint |
| **without the entry** | nowhere — `loc: None`, `path: ()`, `unmapped_uuids: ['07808365-…']` | *"this item is not one aipcb generated — it was probably added by hand in KiCad"* |

Which is exactly the wrong answer about the one piece of copper geometry the
toolchain invented by itself. The zone is in the board as
`"J1 finger field, kept clear of pour"`, 20.9 × 5.5 mm on `F.Cu` and `B.Cu` with
`copperpour not_allowed`, and its UUID `07808365-5859-56df-bdf7-867032aa3787` is
`element_uuid("zone", "fingers", "J1")` — a function of the source, like every
other generated identity. The defect surfaced when the *full* suite ran, not when
the M11b tests did: it takes a DRC violation landing on that zone to see it.

The module and the hand recomputation agree to three decimal places, and the widths

## The empirical findings

Eight are in [ADR 0010](../decisions/0010-highspeed.md), written by the session
that measured them. The ones that changed a decision, with what this pass could
confirm:

**The two impedance formulas in this codebase disagree by 8 %** (Finding 1).
Confirmed here at **8.4 %** on the reference stackup. The controlled-impedance path
uses IPC-2141 for both the derivation *and* the audit that later checks it, because
an audit that recomputes the target with a different formula audits the arithmetic
rather than the board. Hammerstad stays on the M8 `estimate_gap` path so no
pre-M11 board changes geometry — which the byte-identical goldens confirm.

**`layout.stackup.layers` was decorative and had to stop being** (Finding 2). The
block had been in the schema since M1 and nothing derived geometry from it; the
uniform-dielectric fallback gives 0.48 mm where the prepreg under `F.Cu` is
0.2104 mm, a factor of 2.3 and a 40 % error in the derived width. A declared stack
is now honoured, and only when it is *complete* — a partial declaration is ignored
rather than half-believed, because it looks authoritative and is not.

**Emitting both outline authors produces a board KiCad rejects** (Finding 3). Two
`invalid_outline: self-intersecting` errors plus ten `copper_edge_clearance` ones,
all twelve gone when the footprint's copy is stripped.

**A return via placed by eye costs the pair its coupling** (Finding 5). Placed at
0.925 mm from the transition centre against the 1.007 mm the pair's corridor needs,
the receive pair could not tighten, fell back to two separately routed nets, and
those took detours that cost eight further pairs their coupling. **82 µm, and 9 of
14 coupled runs.** The generator computes the distance instead of choosing it, and
the shipping board places its return vias at 0.9999 mm.

**KiCad normalises a through via's recorded span — and that is the finding that
made the via-stub number real** (Finding 6; commit `e33b0ce`). A via written
`(layers "F.Cu" "In2.Cu")` with a through drill comes back from `pcbnew` written
`(layers "F.Cu" "B.Cu")`. That is not wrong — a through via *is* drilled the whole
way — but it erases the one thing a stub calculation needs, which is where the
signal stopped. **Every stub measured off the filled board therefore came out at
exactly zero: comfortable, and false.** The stub is now taken from the router's own
record of what it drilled, and the filled board is used only for what it is
authoritative about, which is copper. The 0.000 mm in the table above is now zero
because the barrel really does end where the signal does; it is a corrected
measurement rather than an unchanged one, and a test
(`test_a_transition_to_an_inner_layer_leaves_the_rest_of_the_barrel`) makes the
non-zero case fail if the shortcut ever comes back.

**"Parallel" is load-bearing in rule 2.** The first implementation measured the
length of centre-line inside a feature's skirt, which counts going past the end of
a pad as hugging it — 1.11 mm on the QFN escape where the parallel part is the
pad's own 0.875 mm, under the 1.0 mm threshold. The stretch is now counted only
while the distance holds to within one gap of its closest approach.

**An `Edge.Cuts` arc costs the router its clearance** (Finding 7). Arcs are
approximated by 24 chords, and a chord runs inside its arc by the sagitta — 8.13 µm
on the 0.95 mm keying notch. KiCad reported ten `copper_edge_clearance` errors at
0.1419 mm against 0.1500 mm asked for; 0.1500 − 0.1419 = 0.0081 mm, the sagitta to
two significant figures. `RoutingEnvironment.arc_slack` now adds the worst sagitta
on the board to the edge keep-out.

**A fabricator needs web between holes, not daylight** (Finding 8). Two GND vias
0.3250 mm apart left 0.1255 mm of web against a 0.2495 mm minimum;
`merge_overlapping_holes` merged holes that *overlapped*, and the test is now the
drill plus the minimum web.

## Defects found

Six. Four fixed, two recorded and not chased:

* **An `Edge.Cuts` arc's chord approximation ate the edge clearance.** Fixed
  (Finding 7). Surfaced because `pcie-sata` is the first board to hug an arc.
* **Same-net via merging used overlap where it needed web.** Fixed (Finding 8).
  Surfaced from a DRC violation on the same board.
* **Via stubs measured off the filled board were all zero, and wrongly so.** Fixed
  by reading the router's record instead (Finding 6). Surfaced because a test
  asserted a *non-zero* stub for an inner-layer transition and got zero.
* **The card-edge pour keepout had no source mapping.** Fixed in `1e0a6a2`.
  Surfaced when the full suite ran, not when M11b's own tests did.
* **`_repair` can produce a route that crosses another net.** *Not fixed.* Found on
  `PRSNT` before that net was dropped: the second-pass repair in
  `route/plan.py::_repair` routed it across two already-placed `REFCLK` tracks and
  KiCad reported two `tracks_crossing` errors. The repair builds its private field
  from the base environment *plus* everything placed so far, so the copper it
  crossed *was* in the obstacle set — something between that field and the realized
  geometry is not honouring it. Recorded in `docs/roadmap.md` rather than left as a
  surprise. It does not manifest on any bundled example today: `pcie-sata` runs 16
  `route-repaired` second passes and comes back with 0 DRC errors. **It is router
  work, it is unexplained, and it is the most serious thing in this report that is
  still open.**
* **The skew reporting wart** described above: one pair, three warnings, two
  different numbers, no label. Found in this measuring pass; not fixed, because
  this pass documents rather than changes.

## Deliberately not built

Recorded in [`docs/roadmap.md`](../roadmap.md) and ADR 0010:

* **Electromagnetic simulation and eye-diagram prediction.** M11e is rule-based
  geometry and says so in its own first line, in `summary.highspeed.method` and in
  the README. Exporting geometry to a solver is M12's subject.
* **Full environment-controlled tightening** beyond the three M11d rules.
* **Back-drilling and blind/buried-via optimisation** for stub elimination. The stub
  is measured and reported; removing it is a fabrication process nothing here
  should commit somebody to by default.
* **Placing the AC-coupling capacitors.** Validated and measured, not moved.
* **Unifying the two impedance formulas.** Kept apart deliberately, because
  changing the old one moves the geometry of every board built before M11.
* **Stripline.** An inner-layer pair gets a microstrip width and no warning.

## What M12 needs to know

M12 is SI simulation, and **it will simulate only the pairs that actually routed**,
so the pair-by-pair table above is its direct input. Concretely:

* **Twelve pair objects are available to simulate**, all coupled, all carrying their
  derived geometry exactly. Nine are inside every budget their class declares; three
  carry a standing wall-hugging flag with the offending feature, its distance and
  the parallel length named; two are over their skew budget by a measured amount.
  Nothing is handed over, so there is no "unrouted pair" case to handle on this
  board — and equally, no example in the repository exercises the M9f hand-over of
  a *controlled-impedance* pair. If M12 needs one, it will have to build it.
* **`summary.highspeed` in `aipcb check --json` is the machine-readable form**, with
  `method` stating in the payload itself that this is not simulation. It carries
  per-pair target and actual width and gap, coupled and uncoupled lengths, skew, the
  reference-gap list and the via-stub list with positions.
* **The reference plane is *declared*, never inferred.** `reference:` on the class;
  `pcie_tx` and `sata` name `In1.Cu` (GND), `pcie_rx` names `In2.Cu` (P3V3, which is
  an AC ground for a decoupled rail and, more usefully, a continuous one). A solver
  wanting the real return path should read that field rather than guessing at the
  nearest plane.
* **The stub number comes from the router, not the board.** Finding 6 above. Any
  M12 code that reads via spans off a `pcbnew`-round-tripped board will get
  `F.Cu`/`B.Cu` for everything and compute a stub of zero for every via on the
  board. This is the single most likely way for M12 to produce a comfortable, false
  number.
* **A board with no `pours:` gets `hs-reference-unchecked` rather than a silent
  pass.** The reference check needs filled copper and therefore ADR 0009's `pcbnew`
  subprocess.
* **`analyse_highspeed(tree, netlist, audits, skew, vias=…, filled=…)` is a pure
  function of a parsed board plus the router's audit records.** It costs 0.11 s on
  the largest board here. A second consumer of the same inputs is cheap.
* **The geometry M12 would export is microstrip only.** Nothing checks that a
  controlled-impedance class is on an outer layer, and an inner-layer pair silently
  gets a microstrip width. If M12 exports geometry for a solver, that is the first
  place the solver and this toolchain will disagree.

Open questions this milestone leaves:

* **`_repair` crossing another net** — unexplained, recorded, not reproducible on
  any bundled example. It is a routing correctness question and it outranks
  everything else on this list.
* **The skew reporting wart** — three warnings, two numbers, one pair.
* **Is 0.125 mm the right intra-pair skew budget for a Gen3 class?** The board
  declares it and misses it by 2.3× on two pairs; the estimate above puts the miss
  at ≈1.8 ps against a 125 ps UI. Either the budget is too tight for what this
  router can deliver through a via transition, or the transition needs to give
  length back. Nobody has decided which, and the report currently just says the
  number.
* **The per-process library-resolution cost**, which M10 called a "fixed ≈2.5 s
  floor". Measured across eleven examples here it is **not fixed**: subtracting the
  warm in-process build from the cold command gives 0.88 s on `congestion`, 2.50 s
  on `ldo-supply`, 3.50 s on `usb-port` and **4.17 s on `mcu-4layer`** — it scales
  with how many distinct KiCad footprint libraries a design touches. It is still the
  largest single cost on seven of the eleven examples, and nobody has looked at it
  in two milestones.
* **Nothing checks that `stackup.planes` and `pours:` agree** — M10 raised it, M11
  made it matter (a `reference:` layer is now validated to be *poured*, which is
  half the check), and it is still not closed in general.
